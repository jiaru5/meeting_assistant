# Local E2E Smoke

本目录提供 manifest 驱动的本地 full-stack/E2E smoke。E2E 注册状态以 `harness/project-manifest.json` 为准。

当前 `smoke-test.sh` 覆盖 P2-C / VS-MA-11 的 deterministic processing local smoke：使用临时 workspace 和脚本内生成的 WAV fixture，通过公开 `processing-cli` JSON/exit code 边界串联 `import_media -> generate_transcript` 内部 normalized audio/source selection -> `generate_speaker_labels -> export_transcript -> delete_session`。

该 smoke 覆盖每步 JSON response、exit code、关键 artifact、`session.json` 变化、原始媒体 checksum、用户显式 export target、confirm=false 失败、workspace 外 export 保留和 workspace 级 `meeting_session.deleted.v1` 删除事件。命令 schema 负向、损坏 `session.json`、session lock、导出 metadata 写失败清理、speaker labels 复用再校验、artifact symlink/hardlink fail-closed 等回归由 `platform/processing-cli/scripts/test.sh` 下的组件测试覆盖。它不调用真实 speaker runtime、不上传/下载外部内容，也不依赖真实会议数据或宿主机常驻服务。

`smoke-test.sh` 的 `VS-MA-20 provider/e2e marker [non-contract]` 输出只用于把 provider smoke 证据归因到 import processing chain 的阶段：no-auto-download dependency preflight、invalid delete exit-code path、import checksum、normalized/transcript artifact、speaker transcript-only fallback/no-auto-upload boundary、export conflict/retention 和 delete retention/event。该 marker 文案不是公开 CLI 命令、字段、artifact、error code 或 exit code 契约。

`capture-processing-smoke.sh` 覆盖 VS-MA-20 provider/e2e 的 native_recording-style artifact chain：通过 test-only `source_type=native_recording`、`status=recorded` workspace fixture，验证默认 `mixed_audio`、`system_audio`/`microphone_audio` fallback、lock/path/temp/checksum rollback、no-auto-download/no-auto-upload 边界、workspace 外 export 保留和 delete event summary。它只证明 processing/e2e 可消费 native_recording 形态的 provider artifact，不证明真实 native capture、native UI 触发、release bundle 或真实 runtime 质量。

同一脚本还输出 `VS-MA-21 provider/e2e marker [non-contract]`，用于标记 test-only capture-style provider failure fixture：公开 `generate_transcript --runtime whisper_cpp` 在缺失 runtime/model env 时返回既有 `dependency_missing` / exit 4，fake whisper runtime 非零失败时返回既有 `processing_failed` / exit 5，并断言失败响应、processing log、capture checksum、derived artifact 污染和 retry success 边界。该 marker 不是公开 CLI 命令、字段、artifact、error code 或 exit code 契约，也不代表真实 native UI、真实 native capture、真实 release bundle 或所有开发机 runtime/model 环境 coverage。

同一脚本的 `capture-style concurrency/retry fixture` marker 用于 VS-MA-21 并发/重试证据：当另一个执行上下文持有同一 session lock 时，公开 `generate_transcript` 必须返回既有 `path_conflict` / exit 3，不登记 `normalized_audio` 或 `transcript_text`，不留下临时输出；释放 lock 后同一 session 重试必须成功生成 transcript，并保持原始 capture artifact checksum 不变。该 marker 同样不是公开契约，也不代表 release-scope 真实 native capture 并发覆盖。

`release-capture-processing-hardening-smoke.sh` 是发布候选路径使用的 VS-MA-21 provider hardening wrapper：它运行同一个 `capture-processing-smoke.sh`，保留完整 stdout/stderr log，再调用 `capture_processing_hardening_report.py --release-scope` 生成结构化 report。成功 report 声明 `release_gate=release-scope-provider-hardening` 和 `not_release_readiness=true`，并逐项记录 no-auto-download dependency preflight、default/fallback capture-style pipeline、path/lock/temp/checksum rollback、provider failure redaction、retry success、capture checksum preservation 和 pass marker 是否存在。该 wrapper 已注册到 `scripts/release-preflight.sh`，但排在 `product-validation-check.py release` 之后；当前发布范围 `PV-MA-*` 仍有 `partial` 时，release preflight 会先 fail closed，不会把 provider hardening wrapper 通过误写成 VS-MA-23 readiness。该 wrapper 不证明真实 ScreenCaptureKit 并发、native UI release-scope 并发、release distribution bundle 或 release readiness。

`release-security-supply-chain-smoke.sh` 是发布候选路径使用的 VS-MA-22 security/supply-chain wrapper：它保留 `security-check`、`supply-chain-check current` 和 `release-provider-smoke` 的完整日志，再调用 `release_security_supply_chain_report.py --release-scope` 生成结构化 report。成功 report 声明 `release_gate=release-scope-security-supply-chain` 和 `not_release_readiness=true`，并逐项记录 production component security reports、supply-chain reports、runtime/model/audio `.local` 边界、model sha256/license/provenance sidecar、required whisper.cpp smoke 和 no-auto-download/no-auto-upload marker 是否存在。该 wrapper 已注册到 `scripts/release-preflight.sh`，但仍排在 `product-validation-check.py release` 之后；当前发布范围 `PV-MA-*` 仍有 `partial` 时，release preflight 会先 fail closed，不会把该 wrapper 通过误写成 VS-MA-23 readiness。该 wrapper 不证明签名/公证分发包、SLSA/release provenance attestation、所有机器 runtime/model sidecar、真实 ScreenCaptureKit 或 release readiness。

`native-capture-artifact-smoke.sh` 是 VS-MA-14/15 的显式 opt-in 跨组件 smoke：只有设置 `MA_NATIVE_CAPTURE_SMOKE=1` 时才调用真实 ScreenCaptureKit `platform/native-app/scripts/native-capture-smoke.sh`，随后用 `processing-cli` 的 workspace contract 读取同一 `session.json` 和四类原始 artifact，校验 `screen_video` checksum、三类音频缺失/降级原因、managed relative path，并在 screen-only 输出无可用音频时断言 `generate_transcript` 以既有 `artifact_missing` fail closed 且不登记 `normalized_audio`、`transcript_text` 或 `speaker_labels`。该脚本默认最多尝试 2 次，底层 native smoke 可用 `MA_NATIVE_CAPTURE_SMOKE_TIMEOUT_SECONDS` 对真实 executable 运行阶段设置超时，失败时保留 summary 并调用 `native_capture_artifact_report.py --failure-report` 生成结构化诊断 report；该 report 汇总 `failure_stage`、start/stop response、validation errors、display wake guard、attempt count、TCC/display/runtime/timeout 诊断和 remediation hints，但保留 native smoke 原始失败退出码。通过时同一生成器会生成结构化 JSON evidence report，默认写入 `platform/e2e/build/native-capture-artifact-smoke/reports/`，也可用 `MA_NATIVE_CAPTURE_ARTIFACT_SMOKE_REPORT` 显式指定路径。默认 report 声明 `release_gate=partial-evidence-only`、`not_release_readiness=true`；成功 report 记录四类原始 artifact 状态、`screen_video` bytes/checksum 校验、音频降级原因、processing `artifact_missing` fail-closed 和无派生产物污染。默认还会用 `MA_NATIVE_CAPTURE_ARTIFACT_SMOKE_DISPLAY_WAKE_SECONDS=120` 和 `MA_NATIVE_CAPTURE_ARTIFACT_SMOKE_DISPLAY_WAKE_SETTLE_SECONDS=3` 启动 `caffeinate -d -u` display wake guard，避免本机显示器休眠把真实 capture 误判为无 display。该脚本不属于默认 full-stack gate；通过也仍是 partial evidence，不证明所有 macOS/TCC 环境、独立音频产物、生产默认真实 capture、native UI 触发 processing provider 或 release readiness。

`release-native-capture-artifact-smoke.sh` 是发布候选路径使用的 VS-MA-14/15 release-scope wrapper：它固定设置 `MA_NATIVE_CAPTURE_SMOKE=1` 和 `MA_NATIVE_CAPTURE_RELEASE_SCOPE=1` 后调用同一个 native capture artifact smoke，使 report 声明 `release_gate=release-scope-native-capture`。该 wrapper 已注册到 `scripts/release-preflight.sh`，但会排在 `product-validation-check.py release` 之后；因此当前发布范围 `PV-MA-*` 仍有 `partial` 时，release preflight 会先 fail closed，不会把 release wrapper 通过误写成 VS-MA-23 readiness。该 wrapper 通过后仍保持 `not_release_readiness=true`，不证明独立系统/麦克风音频真实产物、跨机器 TCC/display 可重复、完整 native-to-processing 成功 transcript 链、真实 Save Panel、release distribution bundle 或 release readiness。

`native-transcript-bridge-smoke.sh` 覆盖 integration-only 的 processing-to-native transcript bridge：同样通过公开 `processing-cli` 生成临时 workspace/session artifacts，保留 `session.json`、`transcript.json` 和 `speaker_labels.json`，再用临时 SwiftPM harness 调用 `TranscriptReviewWorkspaceLoader` 与 `TranscriptReviewViewModel` 只读消费同一 workspace，断言 transcript text、segment count 和 transcript-only degradation 可投射到 native read model。该 Swift harness 还断言 `MeetingAssistantNativeApp.swift` 的 app root 挂载 `DesignedNativeShellView`，而不是直接挂载 primitive debug UI，并验证 designed shell 的 section、`ma.shell.*` locator 和核心子 view wiring。它不注册新 product command、不调用真实 capture、不调用真实 external runtime，也不替代 app-bundle XCUITest locator 覆盖。

`full-stack-smoke.sh` 是 manifest 注册入口，顺序运行 import processing local smoke、native_recording-style provider smoke 和 native bridge + designed shell smoke；当显式设置 `MA_NATIVE_CAPTURE_SMOKE=1` 时，会在 provider smoke 和 native bridge 之间追加真实 native capture artifact smoke；当显式设置 `MA_NATIVE_APP_MVP_FULL_STACK_SMOKE=1` 时，会追加 native app-bundle MVP full-stack smoke，调用 `platform/native-app/scripts/test-app-bundle.sh` 的 `MA_NATIVE_APP_MVP_FULL_STACK_SMOKE=1` 分支，证明 designed shell 可在同一 workspace/session 中触发受控 native recording、provider-owned CLI processing、transcript review、copy/export 和 delete confirmation。默认不设置这些 env 时只输出 optional stage skipped，不尝试 ScreenCaptureKit、macOS TCC 权限或 Xcode UI automation。最终 pass marker 只输出 VS-MA-20 provider/e2e attribution、VS-MA-21 provider/e2e hardening 和 VS-MA-21/22 blocker reminder；这些 marker 不得写作 VS-MA-23 release readiness。VS-MA-20 app-bundle stage 仍是 opt-in partial evidence，不证明真实 ScreenCaptureKit 输出、真实用户 Save Panel、release distribution bundle 或 release readiness；VS-MA-21 hardening summary 只说明 provider/e2e 侧本地命令链、capture-style provider artifact/failure-redaction/retry/checksum 链和 native read bridge / designed shell app-root smoke 通过。发布候选是否可进入人工审查仍以 `./scripts/product-validation-check.py release`、`./scripts/release-preflight.sh` 和验证矩阵中的 `PV-MA-*` 状态为准。`platform/processing-cli/scripts/test.sh` 仍直接调用 processing-owned smoke，避免 processing 组件测试反向依赖 native/Xcode 工具链。

`prepare-smoke-image.sh` 只复用本机已缓存的允许基础镜像并打成本地 smoke tag；它不会在 E2E 执行阶段从外部 registry 拉取镜像。脚本会在有界窗口内反复扫描 target 和允许的 cached base images，以吸收 Docker Desktop image-store 短暂不可用；没有可用缓存时，标准 E2E 应明确失败并提示预加载镜像。

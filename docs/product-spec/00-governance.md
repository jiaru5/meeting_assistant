# 0. 治理

本文件定义 `docs/product-spec/` 的治理规则。相关文件：`README.md`、`10-open-decisions.md`、`11-adr.md`。

> Starter 说明：如果 `PROJECT-STATUS.md` 仍为 `framework` 或 `adoption`，本目录中的示例行只是写法模板，不是项目事实。只有切换到 `project` 后，本目录才可被当成真实项目唯一事实源。

## 唯一事实源

`docs/product-spec/` 是产品和应用技术设计的全局唯一事实源，适用于系统设计、研发实现、测试验收、后续需求和方案变更。

规则：

1. 如果本目录与聊天记录、临时文档、issue、PR、代码注释或旧实现冲突，以本目录为准。
2. 如果本目录与当前代码实现冲突，默认判断为代码需要对齐本目录，除非先确认并更新本目录。
3. 新增或改变产品决策、技术决策、权限、数据模型、事件、API、页面行为或验收标准时，必须先检查与本目录现有内容的矛盾点。
4. 发现矛盾点后，先确认最终决策，再更新本目录，不能只修改代码或另写临时说明。
5. 重要设计决策必须以 ADR 形式追加到 `11-adr.md`，说明背景、决策、影响和替代方案。
6. 新需求开发和方案变更完成后，必须确保领域模型、权限、API、页面、计算规则、数据、事件和验收标准保持一致。
7. 除非创建并明确声明新的替代性规范目录，否则不得把其他文档作为并行事实源。
8. `docs/engineering/` 可以定义仓库结构、命令、测试、CI 和 Docker 交付方式，但不得覆盖本目录中的产品和应用技术事实。
9. `docs/adoption/` 只能作为项目转写工作区，不能替代本目录。原始意向、问答、假设和草稿必须经过用户确认并转写到主责分卷后，才能成为事实。

## 主责分卷规则

1. 每个主题只维护在一个主责分卷。
2. 其他分卷可以引用主责分卷，但不得复制一套可独立维护的规则。
3. 如果需要跨分卷更新，先修改主责分卷，再同步引用分卷和验证矩阵。
4. ADR 只记录背景和取舍；当前可执行规则必须沉淀到主责分卷。

## Spec Sync 分类

每次非平凡改动必须选择一个分类：

| 分类 | 含义 | 必需动作 |
|---|---|---|
| `spec-change` | 新增或改变产品、API、权限、数据、事件、UI 或验收事实 | 先更新主责分卷；重要决策追加 ADR；更新验证矩阵和测试 |
| `spec-covered` | 实现已有事实源定义的行为 | 确认主责分卷已覆盖；更新验证矩阵证据；补测试 |
| `no-product-impact` | 纯工程、重构、测试、脚本或文档导航调整 | 不改产品事实；仍需遵守工程门禁 |

## 变更顺序

1. 定位主责分卷。
2. 判断 spec sync 分类。
3. 如果是 `spec-change`，先更新事实源和 ADR。
4. 更新或确认验证矩阵。
5. 实现代码、迁移、测试或脚本。
6. 运行相关验证。
7. 生成 review report。

## 禁止事项

1. 禁止代码先行发明产品事实。
2. 禁止保留多个互相竞争的 PRD、字段表、API 表或权限表。
3. 禁止把一次性调试记录、执行流水或聊天摘要沉淀为长期事实源。
4. 禁止把测试 fixture、seed 数据或 mock 响应当成产品事实。
5. 禁止用前端权限状态替代服务端授权。
6. 禁止把 `docs/adoption/` 中未确认的假设、原始回答或问题队列直接作为实现依据。
